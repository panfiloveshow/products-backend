# Матрица возможностей API для автопланирования Ozon и Wildberries

Дата проверки: 29 июля 2026 года.

## Короткий вывод

Коммерческий продукт можно построить как единый контур расчёта, но сценарии исполнения должны отличаться:

- Ozon FBO: возможен почти замкнутый цикл — данные → расчёт → предпросмотр → подтверждение человеком → создание черновика/заказа поставки → синхронизация статусов.
- Wildberries FBW: возможны данные → расчёт → проверка доступности товара и направления → XLSX/ручной переход в кабинет → импорт факта поставки. Официальный публичный API не даёт полного цикла создания FBW-поставки и бронирования даты.
- Wildberries FBS — другой процесс. API позволяет создавать FBS-поставки из уже появившихся сборочных заданий, но это не пополнение запасов FBW. Его нельзя выдавать за автоматизацию плановой поставки на склад WB.

## Wildberries

### Что можно получать

| Данные | Гранулярность | Применение | Ограничения |
|---|---|---|---|
| Карточки, артикулы, размеры, баркоды | товар/размер/баркод | единый каталог и корректная строка поставки | артикул без размера недостаточен для одежды и обуви |
| Остатки на складах WB | товар/размер × склад WB | доступный остаток, покрытие, риск OOS | актуальный аналитический endpoint обновляется примерно каждые 30 минут |
| Заказы и продажи | заказ/товар, ограниченная история | скорость спроса, отмены, выкуп | оперативные данные предварительные; гарантированный период заказов ограничен |
| Детализация отчёта реализации | операция/товар | окончательный факт продаж и финансов | появляется позже оперативного спроса |
| Тарифы логистики, хранения и комиссии | категория/склад/дата | экономическая оценка назначения | правила и коэффициенты меняются, нужен версионированный snapshot |
| Коэффициенты приёмки | склад/тип поставки/дата на 14 дней | отбор допустимых дат и складов | доступно только при `coefficient ∈ {0,1}` и `allowUnload=true` |
| Опции приёмки | баркод + количество × склад | финальная проверка, что конкретный набор товара принимается | `POST /api/v1/acceptance/options`, до 5000 позиций |
| Список складов и транзитные направления | склад/маршрут | справочник назначений | не заменяет проверку конкретного товара |
| Уже созданные FBW-поставки, товары, упаковка, статусы | поставка | in-transit и план-факт | API в основном информационный |
| FBS-остатки продавца | товар × склад продавца | доступный общий запас и предотвращение двойного распределения | это не остаток FBW и не входящая поставка |

### Что можно делать

1. Проверять допустимость конкретной матрицы `баркод + количество` для склада.
2. Рассчитывать рекомендации в разрезе региона, склада, артикула и размера.
3. Исключать недоступные направления и учитывать тарифы.
4. Формировать XLSX в формате кабинета WB.
5. Давать прямой переход в кабинет и чек-лист создания FBW-поставки.
6. Читать уже созданные поставки и затем сверять их с рекомендацией.
7. По FBS — создавать поставки из сборочных заданий через отдельный API-контур.

XLSX должен формироваться отдельно для каждого назначения/будущей FBW-поставки. Суммирование одинакового barcode между разными складами уничтожает результат географического распределения.

### Чего нельзя обещать

- Автоматическое создание новой плановой FBW-поставки.
- Автоматическое добавление товаров в FBW-поставку.
- Бронирование даты/слота FBW через публичный API.
- Использование FBS endpoint создания поставки как замены FBW.
- Обход ограничений автоматизацией браузера.

### Обнаруженное несоответствие в коде

Текущий `getAcceptanceSlots()` использует `GET /api/v1/acceptance/options` с датами и `warehouseId`. По официальному контракту это `POST` с телом из баркодов и количеств. Следовательно, текущий метод не может надёжно валидировать план:

- `app/Domains/Wildberries/Api/SuppliesApi.php:196`
- `app/Domains/Wildberries/Api/SuppliesApi.php:212`

В `MarketplaceConstraintSyncService` коэффициент больше 1 считается платным, но физически доступным. Официальная документация WB говорит, что приёмка доступна только при коэффициенте 0 или 1 и разрешённой разгрузке:

- `app/Services/AutoSupplyPlanning/MarketplaceConstraintSyncService.php:284`
- `app/Services/AutoSupplyPlanning/MarketplaceConstraintSyncService.php:321`

Это P0: план может рекомендовать направление, на которое нельзя оформить поставку.

## Ozon

### Что можно получать

| Данные | Гранулярность | Применение | Риск/условие |
|---|---|---|---|
| Товары, offer_id, SKU, штрихкоды | товар | единый каталог | нужна однозначная таблица соответствий |
| FBO/FBS остатки | товар × тип склада/кластер | доступный запас | не смешивать FBO, FBS и собственный склад |
| FBO-отправления | товар × отправление/кластер | спрос, возвраты, фактическая продажа | оперативный источник нужно сверять с финансами |
| Аналитика запасов и оборачиваемости | товар × склад/кластер | покрытие, залежалость | нельзя подставлять первую найденную строку при отсутствии точного склада |
| Кластеры и макролокальные кластеры | кластер | географическая модель назначения | API FBO изменён с 16 февраля 2026 года |
| Заказы поставки и их состав | поставка | in-transit и план-факт | нужна дедупликация с внутренними поставками |
| Доступные интервалы и точки сдачи | поставка/кластер/дата | исполнение плана | зависят от типа прямой или кросс-док поставки |
| Тарифы и финансовые операции | товар/операция | маржинальность и стоимость решения | правила нужно хранить как датированный snapshot |
| Среднее время доставки и география | товар/кластер/период | оценка локальности | методики маркетплейса меняются; это сигнал, а не вечная константа |

Официальные источники:

- [Ozon Seller API](https://docs.ozon.ru/api/seller/)
- [Изменения FBO-поставок и `macrolocal_cluster_id`](https://dev.ozon.ru/news/647-Izmeneniia-v-metodakh-Seller-API-pri-rabote-s-postavkami-FBO/)
- [Ротация API-ключей и рекомендация OAuth](https://dev.ozon.ru/news/649-Obnovlenie-pravil-raboty-s-API-kliuchami-Vazhnye-izmeneniia-v-rabote-s-Ozon-Seller-API/)
- [Требование использовать публичный Seller API](https://dev.ozon.ru/start/298-Seller-API-kak-izbezhat-blokirovok/)

### Что можно делать

1. Построить расчёт `SKU × макролокальный кластер`.
2. Показать предпросмотр распределения и доступных способов поставки.
3. После явного подтверждения пользователя создать черновик или заказ поставки.
4. Получить доступные интервалы и точки сдачи.
5. Синхронизировать статусы, фактический состав, приёмку и расхождения.
6. Связать рекомендацию, созданную поставку и итоговый финансовый результат.

Текущая кодовая база уже содержит значительную часть этого контура: методы предпросмотра, подтверждения, fingerprint, quality gate и создание Ozon draft. Это нужно сохранить, упростить и покрыть contract-тестами.

### Чего нельзя обещать без дополнительной проверки

- Вечную стабильность складских идентификаторов и маршрутов: в 2026 году Ozon перевёл часть FBO-контрактов на макролокальные кластеры.
- Надёжную работу только на постоянных API-ключах: новые ключи живут 180 дней; нужен OAuth или управляемая ротация.
- Экономический эффект от «локальности» по неизменной формуле: тарифы и правила площадки меняются.
- Автоматизацию кабинета через Selenium/Playwright вместо публичного API.

## Обязательные технические контракты

### Общий контракт факта

Для каждого источника хранить:

- `source`;
- `integration_id`;
- `marketplace`;
- `fetched_at`;
- `period_from` / `period_to`;
- `contract_version`;
- `payload_hash`;
- количество записей;
- статус полноты;
- последнюю ошибку;
- лимит/время следующего запроса.

Расчёт должен ссылаться на неизменяемый snapshot всех использованных фактов.

### Marketplace-адаптеры

```text
PlanningCore
  ├── WbFbwAdapter
  │     ├── barcode/size mapping
  │     ├── region/warehouse mapping
  │     ├── tariffs and acceptance coefficients
  │     ├── POST acceptance/options validation

  └── OzonFboAdapter

        ├── macrolocal cluster mapping
        ├── supply availability/timeslots
        ├── preview + confirm
        └── draft/order creation + status sync
```

## Правила fail-closed

Исполнение и экспорт блокируются, если:

- остатки, спрос или справочник товаров старше установленного SLA;
- есть неоднозначное соответствие SKU/баркода/размера;
- направление не прошло marketplace-specific validation;
- строка рассчитана по чужой интеграции или общему legacy-факту;
- расчёт не воспроизводим по snapshot;
- quality gate равен `bad`;
- Ozon credential истёк или срок действия скоро закончится;
- WB acceptance option не подтверждён для фактического количества.

## Рекомендуемый SLA данных

| Источник | Норма | Блокировать исполнение после |
|---|---:|---:|
| Остатки маркетплейса | ≤ 2 часов | 6 часов |
| Заказы/оперативный спрос | ≤ 2 часов | 12 часов |
| Поставки в пути | ≤ 2 часов | 6 часов |
| WB коэффициенты приёмки | ≤ 1 часа | 2 часов |
| Тарифы | ≤ 24 часов | 72 часов |
| Каталог и баркоды | ≤ 24 часов | при обнаружении расхождения |
| Финансовый факт | ежедневно | 72 часа |

SLA должен быть конфигурируемым и отображаться пользователю, а не оставаться скрытой серверной настройкой.
