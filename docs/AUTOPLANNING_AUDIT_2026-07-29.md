# Аудит раздела «Автопланирование» (Ozon + WB) и план коммерческого продукта

Дата: 29.07.2026. Источники: код `products-backend` (main), фронт `front2/frontend-from-server`, публичные материалы конкурентов, документация Ozon Seller API / WB API (по коду клиентов + открытые источники; `dev.wildberries.ru` отдаёт 498 для машинного доступа, проверялось через зеркала и библиотеки).

---

## 0. Вердикт в одном абзаце

Движок написан **под Ozon и работает как инженерный инструмент**, а не как продукт: 21 600 строк расчётного кода, ~30 API-ручек, 40 параметров на создание плана, 7 режимов, 12 бизнес-статусов. Для Ozon математика реально считает спрос по кластерам из отправлений — это уровень выше конкурентов. Для **WB расчёт математически неверен**: спрос каждого склада равен полному спросу SKU, поэтому потребность завышается примерно в число складов. Продукта «нажми — получи поставку» нет ни там, ни там: пользователю показывают матрицу фактов и просят самому выбрать режим, множители сезонности/тренда, кластеры и файл ограничений. Ниже — что чинить, что достать из API, что делают конкуренты и как собрать из этого коммерческий продукт.

## 2. Критические дефекты (по убыванию ущерба)

### 2.1. WB: спрос склада = спрос всего SKU → потребность завышена кратно
`app/Jobs/SyncInventoryJob.php:480-505`:
> «avg_daily_sales и sales_* — суммарно по всем складам SKU. **Записываем одинаково на каждый склад**, в matrix() используется MAX() для агрегации».

`app/Jobs/SyncSalesJob.php:132-151` делает то же самое повторно (общий SKU-спрос на каждую строку склада) и вдобавок считает `days_of_stock` от **суммарного** остатка (`:140`).

В расчёте плана WB-строка создаётся на каждый склад, а `demand_daily` берётся из `average_daily_sales` этой строки (`CalculateAutoSupplyPlanJob.php:477`). Ozon от этого спасён отдельной загрузкой спроса по кластерам; **у WB такой компенсации нет**. Итог: при 4 складах с остатком план просит ≈4× реальной потребности минус остатки. Перераспределение между складами для WB запрещено (`:1580`), схлопывания строк нет.

Данные для правильного расчёта **уже получаются из API**: `app/Domains/Wildberries/Api/SalesApi.php:199 getSalesByWarehouse()` возвращает продажи по SKU × склад отгрузки — и сумма схлопывается в `SyncInventoryJob`. Это правка на уровне одного метода записи, не на уровне архитектуры.

### 2.2. WB: гео-спрос по регионам покупателей не используется в планировании
`SalesApi::getSalesByRegion()` (`:489`) уже разбирает `oblastOkrugName` (округ доставки) и `warehouseName` — но результат идёт **только** в расчёт индекса локализации. Главный вопрос продукта («на какой склад везти») для WB решается ранжированием складов без профиля спроса по регионам, тогда как это ровно то, чем продаётся Поставыч.

### 2.3. Планы никогда не пересчитываются сами
`CalculateAutoSupplyPlanJob::dispatch` вызывается только из контроллера (`AutoSupplyPlanController.php:264,686`). В расписании — обновление фактов (3 раза в сутки), план-факт, алерты, но **не пересчёт планов**. Сервис пополнения запасов, который не пересчитывается ежедневно, не может быть операционным инструментом: пользователь обязан вспомнить и нажать.

### 2.4. Улучшения точности выключены флагами
`config/autoplanning.php`: калибровка прогноза по план-факту `enabled=false`, OOS-коррекция при неизвестном `days_in_stock` — `false`. То есть накопленная механика точности в проде не влияет ни на что. Для продукта, который продаётся точностью, это потеря главного аргумента.

### 2.5. План-факт для WB не считается
`PlanFactReconciler` берёт факт продаж из `postings`, а WB-отправления синкаются только по FBS (`PostingService.php:412` — `/api/v3/orders`). Для FBW фактов нет → `insufficient_data`. Значит и калибровка, и метрика «точность прогноза» на WB нерабочие.

### 2.6. UX требует аналитика, а не селлера
- 40 параметров в `StoreAutoSupplyPlanRequest` (режим, горизонт, min/target/max cover, safety, turnover limit, бюджет, lead time, α EWMA, множители сезонности и тренда, promo_mode, anchor, стратегия локальности, файл ограничений…).
- 7 режимов планирования (`anti_oos`, `balanced`, `cash_safe`, `protect_oos`, `improve_locality`, `max_profit`, `post_promo_careful`) — пользователь не знает, чем `anti_oos` отличается от `protect_oos`.
- Главный экран (`AutoSupplyPlansPage.tsx`, 3 108 строк, инлайн-стили) — это **матрица фактов**: остатки, продажи, оборачиваемость, хранение, кластеры. Ответа «что везти, куда, сколько, когда» на первом экране нет.
- Ручные множители сезонности и тренда — перекладывание работы прогноза на пользователя.

### 2.7. Нет ответа «когда везти»
Коэффициенты приёмки WB (доступны на 14 дней вперёд) и лимиты Ozon есть в данных, но не превращаются ни в дату отгрузки, ни в календарь, ни в уведомление «слот с коэффициентом ≤1 открылся». Для WB это половина боли селлера.

### 2.8. Ozon: перегруз и мёртвый код (проверено 29.07)
Путь Ozon — ~14 900 строк в 6 файлах + 20 сервисов. Ядро считает верно, но:
- `deficit_qty`/`surplus_qty` на агрегированной строке sku×кластер врут: спрос берётся из `MIN(explain_json)` одной под-строки, остаток — `SUM` по кластеру (`AutoSupplyPlanLine.php:272-292` + `AutoSupplyPlanController.php:1694`). `quantity_explanation`/`demand_daily` уже починены через `buildAggregatedExplainMap` (`:1837`) — дочинить те же входы для deficit/surplus.
- Ozon qty-anchor мёртв дважды: `effectiveOzonQtyAnchor()` возвращает `'internal'` безусловно (`CalculateAutoSupplyPlanJob.php:2180-2187`), `$ozonRecommendedSupply` захардкожен `null` (`:884`). Параметр всё ещё в форме и валидации — удалить.
- Legacy v2 shadow-отчёт пересчитывает старый движок по каждой строке на каждом расчёте всех МП (`:1659`) — удалить.
- Блок перераспределения дефицит/профицит не выполняется для Ozon и WB (`:1580`), живёт только для Yandex/generic (~55 строк).
- ~9 последовательных преобразований спроса + 5 капов количества на один SKU; 31 строка с пометками `v2:`–`v6:` в одном job — чинили слоями, не переписывая.
- Контроллер 4 325 строк / 40 методов, job 2 284 строки, территориальный сервис 3 779.

### 2.9. Прочее
- WB `days_of_stock` / `turnover_days` по строке склада бессмысленны (считаются от общего остатка) — но показываются в UI как складские.
- 12 бизнес-статусов плана при том, что до `received`/`reconciled` доходит только Ozon.
- Один и тот же экран обслуживает Ozon (с кластерами и локальностью) и WB (без ничего) — WB-пользователь видит «обрезанный Ozon».

| Сервис | Что делает | Цена |

| **Мастер Поставки** | Расчёт по продажам/остаткам/потребности складов Ozon, **создание поставки через Ozon API**, уведомления о снижении запасов, печать отгрузочных | 3 000 ₽/мес (2 400 при годовой) |
| **Боты автобронирования WB** (bookingwb, fenixwb, roboslot, limitbot) | Мониторинг слотов каждые 2-3 сек, автобронь, лимиты складов | отдельная подписка, первые брони бесплатно |

**Что рынок считает стандартом (must-have):** гео-распределение по регионам покупателей, ADS с поправкой на OOS, учёт «в пути» и возвратов, коэффициенты приёмки, готовый файл для загрузки, Telegram-уведомления, расчёт в 3-5 минут без обучения.

**Чего нет ни у кого (наши козыри, уже реализованные в других модулях):**
1. Планирование **по деньгам**: юнит-экономика по строке (цена, себестоимость, комиссия, логистика, хранение) + ДРР из рекламных кабинетов → «эта поставка принесёт X ₽ прибыли, эта заморозит Y ₽».
2. **Локальность Ozon** с расчётом переплаты за нелокальность и прогнозом КТР — прямая экономия на логистике.
3. **Полный цикл Ozon через API** до этикеток грузомест (у Мастера Поставки — только создание поставки).
4. **Свой склад** как источник ограничения (сколько физически есть у селлера) — конкуренты считают «в воздухе».
5. **Индекс локализации WB** и его влияние на тариф логистики.

## 5. Целевой продукт

### 5.1. Обещание
> «Каждое утро сервис говорит: что везти, на какие склады, сколько, к какой дате — и сколько это даст денег. Один клик — файл или черновик поставки».

### 5.2. Три экрана вместо матрицы

**Экран 1. Пополнение (главный, вместо текущей матрицы фактов)**
- Верх: 4 числа — «Риск OOS: 12 SKU на 340 000 ₽ упущенной выручки за 30 дней», «Заморожено в излишках: 1,2 млн ₽», «Оборачиваемость 163 дн → цель 60», «К отгрузке на этой неделе: 2 340 шт / 890 000 ₽».
- Список **действий**, а не строк данных: `Артикул → везти 120 шт → кластер «Ростов» → до 04.08 (слот ×1) → +38 000 ₽ маржи / OOS через 6 дней`.
- Кнопка на строке: «В поставку».
- Матрица фактов остаётся, но уезжает во вторую вкладку («Данные»).

**Экран 2. Мастер поставки — 3 шага, без параметров**
1. Что везём (авто-набор из дефицита, можно править количества; фильтр «только прибыльные»).
2. Куда и когда (кластеры/склады с обоснованием, для WB — календарь коэффициентов приёмки на 14 дней).
3. Итог: объём, литраж, стоимость закупки, ожидаемая прибыль, срок окупаемости → «Создать черновик Ozon» / «Скачать XLSX для WB».

Все 40 параметров прячутся под «Расширенные настройки». По умолчанию — **один режим «Баланс»** и три пресета: `Не допустить OOS` / `Баланс` / `Беречь деньги`. Остальные четыре режима убрать или свести к пресетам.

**Экран 3. Поставка в работе**
Таймлайн: черновик → слот → отгружено → принято → продано. Внизу — план-факт: «прогноз 300 шт, продано 268, точность 89%». Это то, что удерживает подписку.

### 5.3. Движок: что поменять в математике

**Общее ядро (одно для WB и Ozon):**
```
ADS      = спрос по паре (SKU × точка размещения), OOS-скорректированный:
           продажи за окно / дни, когда товар реально был в наличии
тренд    = автоматически по 7/14/30 (уже есть), сезонность — из истории год-к-году
           (ручные множители — только в расширенных)
SS       = z · σ · √(lead_time)          [уже реализовано, оставить]
target   = ABC-зависимое покрытие         [уже реализовано]
need_i   = ADS_i · (target + SS_days + LT) − stock_i − in_transit_i
```
**Ключевое отличие от текущего состояния:** `ADS_i` — спрос **точки размещения**, а не всего SKU.
- Ozon: уже так (postings по кластерам).
- WB: `ADS_i = ADS_sku × доля_региона_i`, где доля считается по заказам из `supplier/orders` (регион покупателя → ближайший склад-кандидат), а не по историческому складу отгрузки — иначе система будет вечно возить туда, куда возила раньше.

**Распределение по складам WB:** потребность считается на уровне SKU целиком, потом делится по географии спроса, а затем режется ограничениями: коэффициент приёмки, доступность склада, лимит, минимальная партия, объём короба. Ровно та логика, что уже написана для Ozon в `TerritorialPlanningService` — её нужно переиспользовать, а не писать заново.

**Деньги в каждой строке (наш козырь):**
```
маржа_на_единицу = цена − себестоимость − комиссия − логистика(с учётом ИЛ/КТР) − хранение − реклама(ДРР)
приоритет = f(упущенная выручка при OOS, маржа, риск залёживания, коэффициент приёмки)
```
Строки с отрицательной юнит-экономикой — по умолчанию не в поставку, а в отдельный список «сначала почини экономику».

### 5.4. Автоматизация
- Ежедневный пересчёт всех активных планов (cron) + пересчёт по событию «синк остатков завершён».

### Что удалить/заморозить (иначе утонем в поддержке)
- 4 из 7 режимов планирования (`protect_oos`, `improve_locality`, `max_profit`, `post_promo_careful` → пресеты/галочки).
- Ручные множители сезонности и тренда с главной формы (в расширенные).
- Ozon `qty_anchor` (`ozon/min/max/average`) — количество считает наш движок, якорь на рекомендацию Ozon уже помечен deprecated в коде.
- Часть из 12 бизнес-статусов: для WB достаточно `draft → approved → exported → received`.
