# Чек-лист этапа 3: переключение на единый движок спроса

**Назначение:** пошаговый, безопасный план перевода всех потребителей спроса на один
канонический движок (`DemandForecaster`) и удаления legacy. Выполняется ПОСЛЕ прогона
парити на проде. Цель — чтобы исполнение было механическим, а все решения приняты заранее.

**Связано:** [TZ_UNIFIED_DEMAND_ENGINE.md](./TZ_UNIFIED_DEMAND_ENGINE.md) (стратегия), `demand:parity` (измеритель)

**Принцип:** ни одного переключения без (1) данных парити и (2) принятого допуска. Каждый шаг — обратимый.

---

## Фаза A — Сбор данных (на проде, до любого кода)

- [ ] A1. Задеплоить ветку `feat/mp-constraints-autosync` (содержит `demand:parity` и EWMA-фикс).
- [ ] A2. Прогнать парити по каждой активной интеграции:
  ```bash
  php artisan demand:parity --integration=<ID> --top=30 --json=storage/app/parity-<ID>.json
  ```
- [ ] A3. Записать по каждой интеграции из вывода: `median_ape`, `pct_over_25`, `skus_only_canonical`, `skus_only_legacy`.
- [ ] A4. ⚠️ Учесть: EWMA-фикс уже изменил `DemandForecaster` — парити отражает НОВЫЙ canonical. Это правильно (сверяемся с тем, на что переключаемся).

**Выход фазы A:** таблица расхождений по интеграциям.

---

## Фаза B — Решение (gate, бизнес)

Заполнить пороги допуска (предложение по умолчанию — скорректируйте):

| Критерий | Порог GO | Факт (заполнить) |
|---|---|---|
| median APE (медиана интеграций) | ≤ 10% | |
| доля SKU с APE > 25% | ≤ 5% | |
| `skus_only_legacy` (есть у legacy, нет у canonical) | объяснимо/мало | |

**Дерево решения:**
- Все пороги в норме → **GO**, переходим к фазе C.
- Пороги превышены, но расхождение объяснимо (разные источники: postings vs inventory_warehouses; legacy завышает на OOS-днях) → **GO с оговоркой**, фиксируем ожидаемый сдвиг рекомендаций.
- Большое необъяснимое расхождение → **NO-GO**, сначала разобрать причину (где врёт какой движок), не переключать.

- [ ] B1. Пороги зафиксированы.
- [ ] B2. Решение GO / GO-с-оговоркой / NO-GO принято и записано.

## Фаза C — Каркас (код, безопасно, флаг OFF)

Делается только при GO. Поведение НЕ меняется (флаг по умолчанию `off`).

- [ ] C1. **Флаг** `config('autoplanning.unified_demand', 'off')` со значениями: `off` (legacy как сейчас) | `shadow` (считаем оба, логируем расхождение, используем legacy) | `on` (canonical). ENV `UNIFIED_DEMAND=off`.
- [ ] C2. **Интерфейс** `App\Domains\Demand\DemandProviderInterface::dailyDemand(int $integrationId, string $sku, ?string $cluster): float`.
- [ ] C3. **Адаптеры**: `EwmaDemandProvider` (обёртка над `DemandForecaster`) и `LegacyDemandProvider` (обёртка над текущим расчётом legacy). Без смены поведения.
- [ ] C4. **Диспетчер** `DemandProviderResolver`, который по флагу отдаёт нужный провайдер; в режиме `shadow` считает оба и пишет в лог `storage/logs/demand-shadow.log` строку `sku, cluster, canonical, legacy, ape`.
- [ ] C5. Юнит-тесты: `off`→legacy, `on`→canonical, `shadow`→legacy+лог (с моками провайдеров).

**Выход фазы C:** каркас есть, флаг off, прод не затронут.

## Сводная последовательность

```
A (парити на проде) → B (решение допуска) → C (каркас, флаг off)
   → D (shadow, наблюдение) → E (переключение по одному) → F (уборка legacy)
   G (авто-план) — параллельная отдельная подзадача
```

**Оценка кодовой части (C–F):** ~5–6 дней. **G:** +2–3 дня. Всё за флагом, каждый шаг обратим без деплоя.

## Открытые вопросы к решению (фаза B)
1. Точные пороги допуска (median APE, доля>25%).
2. Есть ли per-workspace override флага для пилота, или сразу глобально.
3. Судьба `skus_only_legacy` — это товары, которые canonical «не видит» (нет в postings): дозаполнять или принять.
4. Учёт возвратов/отмен единообразно (связь с памяткой `ozon_returns_effective_logistics`).
